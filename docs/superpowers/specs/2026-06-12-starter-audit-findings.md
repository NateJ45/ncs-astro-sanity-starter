# AUDIT

## core-code
Core code quality is generally solid: the sanityFetch guard, the sectionCadence classifier, SanityImage's srcset handling, PortableText's accessible mark components, and the ContactForm's draft-persistence and honeypot pattern are all well-executed. The main quality gap is a tradeoff between defensive `any` typing and the generated sanity.types.ts — the generator ran and produced accurate types, but they are largely unused at the component and page layer, concentrating type-system risk in the SectionRenderer-to-section-component boundary and in journal page iteration. Two operational concerns stand out: getSiteSettings is fetched redundantly (twice per journal detail page, once per every other page) and ServiceAreaMap silently renders the wrong city for every new client because its geo coordinates are hardcoded rather than wired to the businessInfo fields that already exist in Sanity. The schema.org business-type hardcode is the highest-impact reskin gap for the agency use case.

- [medium/bug] [verified] getSiteSettings fetched twice per journal detail page build
  file: src/pages/journal/[slug].astro
  detail: Lines 40 and 70 both call getSiteSettings().catch(() => null) — once inside getStaticPaths() to check journal visibility, and again at line 70 in the page data-loading block. On a build with many journal entries, this doubles Sanity round-trips for the siteSettings singleton. sanityFetch already wraps client.fetch, but there is no request-level cache; the GROQ comment at line 10 ('Astro caches each call per slug') applies to page-scoped data, not to singleton queries that share the same key across all pages.
  fix: Move the visibility check out of getStaticPaths (or pass the siteSettings result as a prop from getStaticPaths so the page-level call can skip it). The simplest fix: hoist the getSiteSettings result into a module-level lazy singleton that memoizes the first resolved value within a single build process, or accept siteSettings as a prop from getStaticPaths (Astro supports this pattern).
- [medium/bug] [verified] Pervasive `as any` casting on SectionRenderer block properties erases generated Sanity types
  file: src/components/SectionRenderer.astro
  detail: SectionRenderer has 24 `as any` casts on block property accesses (e.g. `s.backgroundImage as any`, `s.primaryCta as any`, `s.services as any[]`, etc.). sanity.types.ts has generated types for HeroSection, CtaBandSection, ImageTextSection, etc. — all the block shapes. Because the classified rows are typed as `SectionBlock` (just `_type: string` + index signature), none of the generated types flow through. A mistyped field name (e.g. renaming a Sanity field in schema without updating the renderer) would silently pass the TypeScript compiler.
  fix: Create a discriminated union type from the generated schema types (`type PageBuilderBlock = HeroSection & { _key: string } | CtaBandSection & { _key: string } | ...`) and use it as the element type in `classifySections`. SectionRenderer can then narrow with type guards per `_type` arm, which eliminates the `as any` casts and makes schema renames a compile error rather than a runtime blank.
- [low/bug] [REFUTED] journal/index.astro maps entries with `: any` despite generated types being available
  file: src/pages/journal/index.astro
  detail: Lines 47, 77, 99: categories and entries from getAllJournalEntries/getAllJournalCategories are typed as `any` at usage sites. The queries return typed arrays (getAllJournalEntries returns based on JOURNAL_CARD_PROJECTION which matches the JournalEntry shape in sanity.types.ts). The same pattern appears in [slug].astro lines 140 and 238. This means a schema change to journalEntry (e.g. renaming coverImage) would silently compile without error and only fail at runtime.
  fix: Define an interface or import the relevant type from sanity.types.ts for the projection shape. For getAllJournalEntries, add a `JournalCard` interface (analogous to the existing `CoreProjectCard` in queries.ts) that matches JOURNAL_CARD_PROJECTION's fields and use it as the return type annotation. This makes the map callbacks typed without any structural changes.
  refutation: The `: any` annotations at the cited lines (index.astro 47, 77, 99 and [slug].astro 140, 238) are real and present, but the reviewer's premise is wrong: getAllJournalEntries() and getAllJournalCategories() carry no explicit return-type annotations and infer Promise<never[]> (empty-array fallback `[]` → `never[]`), not a typed JournalEntry[] array. The JournalEntry type in sanity.types.ts is not wired into those query functions at all — queries.ts line 6 even comments "Types: until `sanity typegen generate` runs, return types are `any`." The `: any` casts are a real code-quality issue, but the specific claim that they exist "despite generated types being available" for those functions is inaccurate.
- [medium/improvement] PortableText rendered as a React island where static HTML is sufficient
  file: src/pages/privacy.astro
  detail: Line 73: `<PortableText client:visible value={page!.body} />` forces the full @portabletext/react bundle to be downloaded and hydrated in the browser just to render static privacy policy copy that will never change after first paint. The same pattern appears in contact.astro line 133 (the what-to-expect/roadmap fallback rich text). Both are below-the-fold content whose output is deterministic at build time. This adds unnecessary JS weight to two pages where there is no interactive requirement.
  fix: Implement a thin Astro server-side Portable Text renderer for simple block content (normal paragraphs, h2/h3, lists, bold/italic, links) and use it in privacy.astro and contact.astro instead of the React island. The JournalPortableText island is correctly left as client:visible because it includes interactive blocks (BeforeAfterSlider). Keep PortableText as a React island only for pages that genuinely need client interactivity or the custom interactive block types.
- [medium/improvement] getSiteSettings query fires 11+ separate GROQ calls instead of being cached at the layout level
  file: src/lib/queries.ts
  detail: Every page independently calls getSiteSettings() (confirmed in 11 pages). The getSiteSettings query is substantial: it projects siteSettings plus 9 separate sub-queries into businessInfo for flat field names (lines 115-132). At build time, Astro's static build parallelizes page rendering, so these do not collapse — each page pays for its own GROQ round-trip. The comment at queries.ts lines 103-108 acknowledges the dual-source shape, but the query is still a fan-out of 9 inner `*[_type == 'businessInfo']` sub-queries inside a single outer query, meaning a total of 10 Sanity reads per page.
  fix: Either (a) cache the result in a module-level singleton (lazy init on first call, same build process) so all pages share one resolved value, or (b) collapse the 9 businessInfo sub-queries into a single `*[_type == 'businessInfo'][0]` fetch and merge at the application layer, then cache. Option (a) is the low-impact change: add a module-level `let _siteSettings: Promise<...> | null = null` and return the memoized promise on subsequent calls.
- [medium/feature-gap] ServiceAreaMap coordinates and bbox are hardcoded placeholders with no Sanity connection
  file: src/components/ServiceAreaMap.astro
  detail: Lines 21-23: bbox, markerLat, and markerLon are hardcoded to Indianapolis-area coordinates with only a code comment to update them. The contact.astro page renders ServiceAreaMap with no props (line 197), so every client site shipped from this template will silently show the wrong city on the map until a developer hand-edits the component. There is no path for a non-developer (e.g. Staci the editor) to update this, and the Sanity businessInfo document already stores geoLat/geoLng (visible in the schema at queries.ts lines 155-156) that could drive it.
  fix: Pass the coordinates from siteSettings into ServiceAreaMap as props in contact.astro. The data is already fetched: `siteSettings.geoLat` and `siteSettings.geoLng` are populated by getSiteSettings() via the businessInfo sub-query. Add those as optional props with the current hardcoded values as fallbacks, so fresh clones still render something visible. This turns a code-edit requirement into a Sanity Studio field that Staci can update.
- [medium/feature-gap] `@type: 'InteriorDesigner'` in LocalBusiness schema is interior-design-specific and will be wrong for most clients
  file: src/lib/schemas.ts
  detail: Line 54: `'@type': 'InteriorDesigner'` is hardcoded in localBusinessSchema(). This type is appropriate for the original Reid Design client but not for a plumber, accountant, photographer, or non-profit. Since the template goal is to serve any service business or non-profit, every site cloned from this starter will emit schema.org markup that misidentifies the business type. Google's Rich Results parser uses this to determine search eligibility.
  fix: Add a `businessType` field to the siteSettings Sanity schema (dropdown of common schema.org LocalBusiness subtypes: LocalBusiness, ProfessionalService, HomeAndConstructionBusiness, LegalService, MedicalBusiness, etc.) with a fallback of 'LocalBusiness'. Read it in localBusinessSchema() as `s.businessType ?? 'LocalBusiness'`. Alternatively, read it from brand.config.json (which already drives the reskin) so it is set once during the brand pass.
- [low/improvement] makeComponents() re-creates component map and heading-dedup state on every PortableText render
  file: src/components/PortableText.tsx
  detail: Line 160: `<PT value={value} components={makeComponents()} />` calls makeComponents() on every render, which allocates a new `seen` Map and a new closured `headingId` function on each React reconciliation. The seen Map is intentionally per-render (so heading ids stay unique within one render), but the constant re-allocation of the full components object causes React to treat all PortableText components as new objects each render and skip the referential-equality shortcut for components it uses internally. The same pattern exists in JournalPortableText.tsx line 442.
  fix: Move the components factory inside a `useMemo` call (for the React component context) or, since PortableText.tsx is only ever rendered as a `client:visible` island where state stability matters, stabilize the reference: `const components = useMemo(() => makeComponents(), [])`. Because the seen Map is intentionally scoped to a render and the component mounts once per island, a single-dep empty-array memo is correct and eliminates the allocation churn.

## sections
The section block library has a solid foundation: 17 block types across general and rich sets, good surface-cadence separation, idPrefix collision protection, and graceful empty-state handling throughout. The core components (SectionHeading, SanityImage, PortableText, CtaLink) are reused consistently, and the heading hierarchy defaults correctly to h2 for section headings. Two correctness issues were found: GalleryGrid and VideoEmbed emit unlabelled landmark regions when no heading is set, and the VideoEmbed iframe is missing `fullscreen` in its Permissions Policy allow attribute. The most significant gaps are structural: the existing FaqAccordion component is not wired as a page-builder block (forcing hard-coded pages or from-scratch work per client), there is no team/staff grid block (blocking every multi-person client), and there is no logo strip or inline embed/form block. These three gaps are the highest-leverage additions for serving a broad range of service businesses and non-profits quickly. A shared-helpers extraction for the duplicated proseBody/imageWithAlt would reduce per-fork maintenance cost.

- [medium/bug] [verified] GalleryGrid and VideoEmbed render an unlabelled <section> when no heading is provided
  file: src/components/sections/GalleryGrid.astro
  detail: GalleryGrid (line 34) sets `aria-labelledby={heading ? headingId : undefined}`, which means a headingless gallery emits a `<section>` with no accessible name at all. VideoEmbed (VideoEmbed.astro line 43) has the same pattern. Screen readers announce unlabelled landmarks as generic regions with no context, which fails WCAG 1.3.6 (Identify Purpose) for landmark regions. An editor dropping a gallery or video without a title produces a silent landmark.
  fix: Add a fallback `aria-label` when no heading is supplied. For GalleryGrid: `aria-labelledby={heading ? headingId : undefined} aria-label={heading ? undefined : 'Photo gallery'}`. Apply the same fix to VideoEmbed. Both are marked 'Safe to edit by hand'.
- [high/feature-gap] [verified] FAQ block exists as a standalone page only; no page-builder block wires FaqAccordion into the section library
  file: src/components/FaqAccordion.tsx

But there is no `faqSection` block in sections.ts / richSections.ts and no case for it in SectionRenderer.astro. The result: an editor cannot drop a mini-FAQ accordion into the middle of any other page (home, services, about, custom /slug pages). This is the single highest-leverage missing block for service businesses: embedding "3 common questions" on a services or about page is nearly universal.
  fix: Add a `faqSection` page-builder block (eyebrow, headline, optional subhead, array of reference to `faq` doc type OR inline question/answer pairs, optional CTA). Wire it as SELF_CONTAINED in sectionCadence.ts so it manages its own bg-muted surface. Add a `FaqSection.astro` wrapper around the existing FaqAccordion island and add the case to SectionRenderer.astro. This requires zero new components -- just a thin schema block and a three-line renderer mapping.

  file: studio/schemaTypes/sections.ts

Every second brochure site for a service business or non-profit includes a row of client logos, press badges ('As seen in'), accreditation seals, or partner marks. - [low/bug] [verified] VideoEmbed iframe missing 'fullscreen' in the Permissions Policy allow attribute

## schemas
The schemas are well-structured overall: field groups are used consistently on complex documents, previews are present on every type, required/optional validation is thoughtful, Portable Text blocks are appropriately scoped per context, and the two-field approach (siteSettings for identity/infrastructure, businessInfo for operations) is a clean architectural split. The editor experience improvements in the journal entry (groups, inline blocks, Canvas hints) and the studioGuide/studioNotes onboarding panels are genuinely agency-quality. The main failure modes fall into three categories: two genuine data bugs (duplicate testimonial source fields, missing ctaBlock internal link targets) that will surface on every project; two constraints that hard-bake interior-design assumptions into the schema (faqItem categories, service CTA default text) and require code changes for any other business type; and two gaps in coverage (limited social links, single-location assumption in businessInfo) that break for common non-interior-design clients such as remote services businesses, multi-location firms, and non-profits. The missing portfolio schema is a potential silent runtime failure for any agency team that enables the portfolio page without reading module docs.

- [high/bug] [verified] faqItem category is a hardcoded list — breaks for non-interior-design clients
  file: studio/schemaTypes/faqItem.ts
  detail: The `category` field uses a closed options list with interior-design-specific values: 'Pricing & Cost', 'The Process', 'Logistics', 'Service Area', 'Getting Started' (lines 72-79). Any client whose FAQ structure does not map to these five buckets — a non-profit, a multi-service firm, a law office — either lives with wrong labels or needs a code edit to the schema. - [high/bug] [REFUTED] Duplicate source/sourceType fields on testimonial — editor confusion and data split
  file: studio/schemaTypes/testimonial.ts
  detail: The testimonial schema has two near-identical fields: `source` (lines 40-49, a required dropdown with layout 'list') and `sourceType` (lines 79-89, an optional radio with slightly different values — 'Direct' vs 'Direct (email or text)'). Both represent the review platform. An editor filling in a new testimonial will set one or the other, and queries must defensively handle both.   fix: Merge into a single field. Keep `source` (it already has validation), add 'Direct' as a normalized value, hide `sourceType` as `hidden: true, readOnly: true` per the template's rollback-safety convention, and add a migration note in the comment header. The front-end badge component should read only `source`.
  refutation: Both `source` (lines 36-50, required dropdown, no explicit layout) and `sourceType` (lines 75-89, optional radio) exist on the schema, but they are not duplicates — the frontend uses them for distinct UI slots: `source` populates the attribution meta line in both TestimonialCard.astro and FeaturedTestimonial.astro (line 49/51), while `sourceType` drives a separate badge element (line 61 in each). The reviewer's framing of "near-identical fields for the same purpose" is inaccurate; the differentiation is intentional and reflected in both schema descriptions and component code. The line numbers are slightly off (source field starts at line 36, not 40), and `source` has no `layout: 'list'` option set. The value mismatch ('Direct (email or text)' vs 'Direct') is real, as is the lack of validation on `sourceType`, but an editor filling a new testimonial is guided to use both fields for different reasons — not the same one twice.

- [medium/bug] [REFUTED] testimonial `featured` boolean has no enforced uniqueness — multiple featured testimonials silently conflict
  file: studio/schemaTypes/testimonial.ts
  detail: The `featured` field (lines 68-74) warns editors 'Only one should be featured at a time' in the description, but there is no validation rule preventing two or more testimonials from having `featured: true`. When that happens, both pass schema validation and it becomes query-layer Russian roulette — whichever document sorts first wins. This is a common editor mistake on any CMS with a 'featured' boolean pattern.
  fix: Add a custom async validation rule on `featured`: `Rule.custom(async (value, context) => { if (!value) return true; const { document, getClient } = context; const count = await getClient({ apiVersion: '2024-01-01' }).fetch('count(*[_type == "testimonial" && featured == true && _id != $id])', { id: document._id }); return count === 0 ? true : 'Another testimonial is already featured. Uncheck the other one first.'; })`. This fires on publish and prevents silent conflicts.
  refutation: The `featured` boolean on testimonial.ts (lines 68-74) does indeed have no validation rule — only a description warning — so the uniqueness gap is real. However, the claimed consequence is wrong: no GROQ query ever filters on `testimonial.featured == true`. The front-end obtains its featured testimonial via an explicit `featuredQuote` reference field on the `testimonialsSection` block (studio/schemaTypes/richSections.ts line 197-202), resolved in the sectionsProjection in src/lib/queries.ts. The `featured` boolean is effectively vestigial — it only drives a studio badge in documentBadges.tsx — so multiple documents having `featured: true` causes no query-layer conflict whatsoever.

  file: studio/schemaTypes/index.ts

## docs
The documentation is structurally strong: the three-tier architecture (CLAUDE.md as always-loaded constitution, OPERATIONS.md as tactical playbook, docs/bootstrap/ as onboarding runbook) is clear, and the per-module enable guides and pre-launch checklist are thorough. The biggest quality gap is a stale-state problem from the Phase B upgrade: when `process` graduated from a module into a core always-on route, the module-facing docs (docs/modules/README.md, docs/modules/process.md, docs/agent/page-architecture.md, and the preset descriptions) were not all updated to reflect this, leaving a developer who reads docs/modules/README.md with instructions to 'enable' a route that is already live. The second most impactful inaccuracy is a recurring false claim across three files that `npm run build` chains typegen first — it does not; that is `build:full`. This will silently cause type-staleness bugs if a developer trusts the docs and skips the separate `npm run typegen` step after schema changes. The webhook onboarding gap (Cloudflare deploy hook URL is never explained in the runbook's step 10) and the missing Cloudflare account setup step are the most likely first-time blockers for a new agency developer following only NEW-PROJECT.md. Module counts are inconsistent across four files (9, 10, or 11 depending on which doc you read).

## seo-a11y
The SEO and structured-data foundations are strong: BaseLayout correctly emits canonical URLs, OG meta with a robust four-level fallback chain, a well-structured JSON-LD injection pipeline (LocalBusiness on every page, BreadcrumbList on every internal page, BlogPosting and FAQPage on their respective pages), and the sitemap integration is properly wired. Accessibility has clear wins: the skip link is correctly implemented, prefers-reduced-motion is comprehensively honored across Lenis, CSS animations, and JS observers, and focus-visible rings are consistently applied to most interactive elements. ## dx

## heavyweight
RECOMMENDATION: All five libraries are poor-to-workable fits for this template's core constraint, and none should be adopted as a general-purpose component source. The template's shadcn copy-in model (vendor components into src/components/ui/, style with Tailwind referencing :root semantic tokens, zero JS for static components) is architecturally superior for a brochure site and should remain the default path.

The generic advice recommending Mantine for this stack is wrong. Mantine requires MantineProvider as a mandatory React Context wrapper per island, uses its own --mantine-* CSS variable namespace that is completely blind to the :root reskin, and adds ~140 kB gzipped to a bundle that should stay under 100 kB total. Reject it for standard brochure components.

If a specific complex interactive widget cannot be assembled from radix-ui + cva (the library already installed), the two options worth considering are:

1. HeroUI v3 (workable, with effort): No Provider required — the only library here that clears that bar. CSS-first Tailwind v4 architecture. Use it for a specific island (complex combobox, a date range picker) where radix-ui primitives are too low-level. The blocker is CSS variable naming collision with the template's shadcn tokens (--background, --primary, --foreground overlap). Scope HeroUI to a [data-heroui] subtree or import its styles inside a CSS @layer beneath globals.css to prevent the collision. Do not adopt as a general component library — the token conflict makes it incompatible with the one-pass reskin at the global scope.

2. PrimeReact v11 unstyled/Passthrough mode (workable for complex behavior-heavy widgets): The only library that can be styled entirely with Tailwind semantic tokens and therefore participates in the one-pass brand reskin. Worth adopting narrowly for widgets with no radix-ui equivalent — rich data tables, tree selects, file upload with progress, complex schedulers. Requires a PrimeReactProvider wrapper per island (thin, but real) and upfront work authoring the Tailwind passthrough config. Do not use styled mode — it breaks the reskin.

Chakra UI v3 (still CSS-in-JS at runtime, Provider required, parallel theme object) and Ant Design v6 (enterprise visual language, large bundle, Provider required, documented Cloudflare Workers SSR issues) are both poor fits and should not be adopted.

- Mantine v8 [poor] Mantine requires MantineProvider as a React Context wrapper for every component tree — this is a hard architectural requirement, not optional. Astro's official documentation explicitly states that React Context providers cannot be shared across islands, and Mantine's own help docs confirm the library is incompatible with Astro. The only workaround is wrapping each island individually in MantineProvider as a React component (not an Astro layout), which works but carries significant costs: (1) MantineProvider ships its own CSS variable injection via a runtime <style> tag — it generates --mantine-* tokens from its theme object at JS execution time, not at build time; (2) Mantine uses its own --mantine-color-*, --mantine-font-*, --mantine-radius-* namespace, completely parallel to this template's :root/:dark shadcn semantic tokens; (3) the one-pass brand reskin rewrites --primary, --background, --foreground etc. in globals.css — Mantine components are blind to those variables and will never recolor, requiring a second parallel theme configuration in every Mantine island; (4) @mantine/core v7 adds roughly 140 kB gzipped to a bundle even with attempted tree-shaking (documented in GitHub issue #4926), and v8 is not materially smaller — this is catastrophic on a brochure site where the entire page JS budget should be under 100 kB; (5) each MantineProvider instance re-injects the full CSS variable set. A narrow exception exists: a complex booking or scheduling island (e.g. @mantine/dates calendar picker inside a dedicated client island) could earn its weight if no shadcn/radix equivalent is acceptable and the island is fully isolated. But for standard brochure components — heroes, grids, forms, FAQs — Mantine is the wrong tool for this stack.

  theming: Incompatible with the one-pass reskin. Mantine manages its own CSS variable namespace (--mantine-*) injected by MantineProvider at runtime. - HeroUI v3 (ex-NextUI) [workable] HeroUI v3 is the most technically interesting option in this list for this stack — it has made a genuine architectural bet on Tailwind v4's CSS-first approach. v3 dropped its Tailwind plugin in favor of pure CSS file imports and replaced Framer Motion with native CSS transitions (~25 kB gzipped saving). Critically, v3 no longer requires a HeroUIProvider wrapper, making it the only batteries-included library here that works cleanly in Astro islands without a per-island Context hack. Its theming runs on Tailwind v4's @theme / CSS variable layer using OKLCH colors. Additionally HeroUI v3 was still in beta as of early 2026 and the Tailwind v4 integration path required plugin wrapper hacks for earlier beta releases (GitHub discussion #16369). - PrimeReact v11 [workable] PrimeReact v11 is the most nuanced option here. It offers two completely different integration modes. Styled mode uses its own --p-* CSS variable namespace with a three-tier token system (primitive, semantic, component). Unstyled/Passthrough mode completely removes PrimeReact's own CSS and lets you apply Tailwind classes to every internal DOM slot — this is the architecturally interesting path for this template. In unstyled mode, PrimeReact components become accessible behavior shells that you style with Tailwind utilities referencing the template's semantic tokens (text-foreground, bg-card, border-border etc.). This is closer to the shadcn copy-in model than any other batteries-included library here. The cost: unstyled mode requires writing or sourcing a complete Tailwind passthrough configuration, which is non-trivial work (the community primereact-tailwind repo provides a starting point). PrimeReactProvider is still required as a Context wrapper per island, but it is lighter than Mantine/Chakra providers — it primarily handles ripple effects, input styles, and transition options; the Context dependency is thinner. The --p-* styled mode tokens cannot be driven by the :root reskin without manual mapping. For the specific case of complex interactive components not available in radix-ui — a rich DataTable, a TreeSelect, a FileUpload, a complex Scheduler — PrimeReact unstyled mode earns its weight because you get the behavior and accessibility for free while retaining full style control via Tailwind tokens.
