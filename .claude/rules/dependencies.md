# Rule 8: the matched dependency set

Loads when you touch package manifests, Astro/wrangler config or workflows. Moved verbatim from CLAUDE.md.

8. **The Astro / adapter / wrangler / Sanity versions are a MATCHED SET. Do not bump one in isolation.** The pins and the reasons are PORTS.md cards 10, 13 and 14; the short version:
   - `@astrojs/cloudflare` is pinned to exactly **14.4.3**, and `astro` rides with it (`^7.4.4`, since 2026-10-30, PORTS.md card 204; was 14.4.0 with `^7.4.0` from card 97): the adapter imports Astro internals, so a lone `astro` bump can break the build (14.2.4 imports `beginContentEntryCollection`, which astro 7.3 removed: `[MISSING_EXPORT]`, PORTS.md card 92). Adapter and `astro` move together, by hand, in a planned stack session. 14.4.3 (like 14.4.0) peers `astro ^7.4.0` and `wrangler ^4.125.0`. It depends on `@cloudflare/vite-plugin` ^1.63.1, which nests its OWN wrangler 4.151 and miniflare 5 beta for build-time prerender only; the deploy CLI is still the top-level `wrangler` 4.129.1 with its own miniflare and workerd (`npm ls wrangler miniflare` shows both).
   - **Node is pinned in `.nvmrc` (22.23.4 since 2026-10-30, PORTS.md card 209), and every workflow's `actions/setup-node` reads it with `node-version-file: .nvmrc`.** Never go back to `node-version: 22`: that takes whichever 22.x the runner image cached, and astro 7.4.4 refuses anything below 22.23.4, so a build passes or fails by which image the job draws. Bump Node by editing `.nvmrc` alone, kept at or above the `engines.node` floor in `package.json` (and the lockfile's root entry), and raise that floor whenever an `astro` bump raises Astro's own.
   - `wrangler` is pinned to **~4.129.0** (4.129.1 installed since 2026-10-13, PORTS.md card 94). The adapter's peer range forces >=4.125.0, and 4.129 is the line the family has already deployed with. Do not jump to the 4.14x line just because it is newer: every wrangler from 4.126 on bundles a miniflare 5 alpha or beta. Adapter v14 has been observed writing `legacy_env: true` into the generated `dist/server/wrangler.json` (mas-monograms, on 14.2.4), and a wrangler that rejects the field fails every deploy; the starter's generated config on 14.3.4, 14.4.0 and 14.4.3 has no `legacy_env` (14.4.3 checked with a real deploy to a throwaway Worker, 2026-10-30). 14.4.0 adds `k2: []` and `upload_source_maps: true`; wrangler 4.129.1 warns `Unexpected fields found in top-level field: "k2"` and carries on (dry run exits 0). The warning is expected, not a failure. Re-check that, with a real `wrangler deploy`, on every adapter or wrangler move, not by reading semver (vault gotcha `wrangler-bump-needs-real-deploy-test`).
   - `react`, `react-dom` and `react-is` are pinned **exact** at 19.3.1 (since 2026-10-18, starter PR #140, was 19.2.7; PORTS.md card 112). Sanity 6.19 already nested 19.3.1 copies under the 19.2.7 pin, and `@portabletext/editor` 8.2.4 peers `^19.2.8`, so the bump collapses those to one copy; `npm ls react react-dom react-is` must show one version, deduped. A mismatch dies inside workerd behind a wall of Miniflare stack frames; the real message, `Incompatible React versions`, is buried **above** the `MiniflareCoreError`.
   - The Sanity set is pinned to a combination known to work **together**, and that is the family's phase-2 set (PORTS.md card 103, refreshed 2026-10-30 by card 204): `sanity` 6.21.0, `@sanity/vision` 6.21.0, `@sanity/ui` **4.4.10**, `@sanity/icons` **5.2.3**, `styled-components` 6.6.0, `@sanity/client` 8.14.1, `@sanity/preview-url-secret` 4.1.5, `@sanity/astro` 3.6.0, `@sanity/themer` 0.10.6, `sanity-plugin-media` 6.6.0, `sanity-plugin-asset-source-unsplash` 7.0.30, `@sanity/orderable-document-list` 2.0.28, plus `sanity-plugin-utils` 2.0.22 and `@sanity/visual-editing` 6.2.0 held through `overrides` (edit both visual-editing entries in one pass or npm refuses with EOVERRIDE). Studio code is written against `@sanity/ui` 4: `gap` not `space`, `gridTemplateColumns` not `columns`, `Menu*` from `@sanity/ui/menu`, `useToast` from `@sanity/ui/toast`, and every icon from its own subpath (`import { BellIcon } from '@sanity/icons/Bell'`; the root exports none, and `astro check` does NOT catch a root icon import, only `astro build` does). Raising the three typescript-eslint ranges in one `npm install` fails with ERESOLVE; install with the old ranges, `npm update` the three, then raise them (card 204). A Studio file from a repo still on the phase-1 set (`sanity` 6.9.1, `@sanity/ui` 3.5.4) does not port without that migration (card 103's notes). **Invariant after any Sanity dependency work:** `find node_modules -path "*@sanity/ui/package.json"` and `find node_modules -path "*@sanity/icons/package.json"` must each print exactly ONE line, and `grep -l "errors.md#" dist/client/_astro/*.js` exactly one file. `react/compiler-runtime` stays in `optimizeDeps.include` in `astro.config.mjs`: `@sanity/ui` is excluded from pre-bundling, and without the include the dev Studio does not hydrate (`does not provide an export named 'c'`); the build cannot show it.
   - **`primereact` is held at 10.x on purpose (2026-10-13, PORTS.md card 94).** v11 is a rewrite into unstyled compound primitives (`Select.Root`, `Select.Trigger`, ...), `PrimeReactProvider` moves to `@primereact/core`, `primereact/api` is gone, and the licence changed from MIT to the PrimeUI License: a licence key is required (free Community tier for under USD 1M revenue, annual renewal) and an unverified key injects a banner into the page. Nothing in the family renders PrimeReact (the `src/components/primereact/` scaffold is imported by no page), so there is no gain to set against a licence obligation. Take v11 only as a deliberate decision with a key in hand.
   - Historical, still worth knowing: `@astrojs/cloudflare` 13.6.0 regressed Astro's image optimizer (optimized images written to `dist/client/_astro/` while the optimizer read `dist/_astro/`), which is why 13.5.5 was pinned before this upgrade. **Verify image output paths after any adapter bump.**
   - **`session: false` in `astro.config.mjs` is load-bearing.** Left on, the Cloudflare adapter auto-declares a `SESSION` KV binding in the generated config, and a KV binding with no namespace id fails the deploy. This template has no login.
   - **No `assets.not_found_handling` in `wrangler.jsonc`.** With `404-page` set, Cloudflare answers navigation requests that miss the asset store from the static 404 page **without invoking the Worker**, which silently 404s every SSR route for real browsers while curl (which sends no `Sec-Fetch-*` headers) sees them working.
   - **The Windows build needs wrangler's workerd, and `npm run build` handles it.** The vite plugin's pinned workerd aborts at prerender on Windows (`std::terminate`), so `scripts/with-workerd.mjs` points `MINIFLARE_WORKERD_PATH` at wrangler's newer binary on win32. It is a no-op elsewhere.
   - **`astro dev` on Windows depends on `fixSanityDedupeAlias()` in `vite.plugins`** (PORTS.md card 60, `src/lib/sanity-dedupe-alias.ts`). `@sanity/astro`'s dev-only `sanity:module-dedupe` plugin builds its `sanity` alias with a forward-slash-only regex, so on Windows it points at `...\node_modules\sanity\package.json` and the dev server dies inside a minute with `[MISSING_EXPORT] ... is not exported by "node_modules/sanity/package.json"`. `astro build` never loads that plugin, so CI and production cannot show it. **Do not remove the plugin, and do not set `SANITY_ASTRO_DISABLE_MODULE_DEDUPE=1` instead**: the server then stays up but the Studio fails to hydrate (`react-compiler-runtime ... does not provide an export named 'c'`). Delete it only once `sanity:module-dedupe` in `node_modules/@sanity/astro/dist` uses a separator-safe replace.
   - **`package.json` `overrides` hold transitive security pins (PORTS.md card 214).** Besides `sanity-plugin-utils` and `@sanity/visual-editing`, the block pins patched copies that a parent fixes at an exact old version (miniflare, `@module-federation/dts-plugin`, `@vercel/frameworks`, linkinator, `@lhci/cli`, `tmp`). Scope an override to the parent and to the same major, run `npm ls` (must exit 0), and delete the entry once the parent ships the patched pin. Dependabot cannot do this itself.
   - **Never run `npm audit fix --force` in this repo.** It reads the matched set above as a set of upgrades it is free to break: its offered fix for the Sanity advisories is a DOWNGRADE of `sanity` from 6.19.0 to 5.14.1, across a major version, which takes the embedded Studio with it. The open advisories are tracked, with the reasoning, in `docs/PENDING.md`.
   - **Never delete or regenerate `package-lock.json`, and use `npm ci` (never `npm install`) for any run whose outcome you will reason from** (PORTS.md card 68). A regenerated lockfile lets hundreds of transitive packages float to whatever is newest that day, and one of them can make `sanity schema extract` (which `npm run typegen` runs) die with the one-line `Error: exports is not defined`, with no module name in the stack. Because the lockfile is regenerated on every run, every candidate change then "reproduces" the failure, and even the pristine baseline fails too, which sent a bisect on a sibling repo down the wrong path for ~3 hours. So: bisect dependency problems with the COMMITTED lockfile in place (change `package.json`, `npm install` to update only the affected subtree, test, then `git checkout -- package.json package-lock.json` and repeat); test each candidate from a clean `git status` or a fresh clone and check `git diff --stat -- package-lock.json` before trusting a result; and let Dependabot propose bumps one package at a time so CI (which runs `npm run typegen`) isolates the culprit, rather than hand-running `npm audit fix` or `npm update` across the tree. If `npm run typegen` dies with `exports is not defined`, suspect the lockfile before the last package you touched.
   - **Dependabot (`.github/dependabot.yml`, PORTS.md card 62) ignores every npm major (`*` + `version-update:semver-major`) and the pinned set** (`sanity`, `@sanity/*`, `sanity-plugin-*`, `react`, `react-dom`, `react-is`, `styled-components`, `@astrojs/cloudflare`, `wrangler`, `astro`, and `typescript` majors `>=7`). `astro` is on the list because the adapter imports Astro internals: astro 7.3 dropped an export that `@astrojs/cloudflare` 14.2.4 imports, so a lone astro minor failed every build (PORTS.md card 92); move it with the adapter. Formatter bumps (`prettier`, `prettier-plugin-*`) come in their own `formatters` group, and `minor-and-patch` excludes them with `exclude-patterns` (a refresh of an older bundle ignores group order), so a reformat reds only that PR; fix it with `npm run format` on the branch. Majors are taken in one planned, starter-first stack upgrade, not from PRs (the `github-actions` ecosystem is exempt). When you move the matched set by hand, the ignore list does not change; when you add a new exact-pinned package, add it to the list in the same commit. Secrets note for forks: `docs/agent/deployment.md`, "Dependabot".
   - **Curling a page is not verifying it.** `/studio` returns 200 with real HTML while being completely broken at React mount. Anything that mounts a client framework has to be opened in a real browser with the console read.
